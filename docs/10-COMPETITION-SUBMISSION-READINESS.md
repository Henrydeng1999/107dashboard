# 比赛验收与提交收尾审查

> 审查日期：2026-08-28
> 审查对象：`107 Dashboard` 比赛 MVP 及 `codex/windows-client` 当前工作区
> 依据：一〇七杯算力平台赛道作品提交预通知（提交截止时间为 9 月 6 日 23:59）

## 一、结论先行

项目代码已经具备比赛演示 MVP 的主要能力：能够围绕真实 Slurm 作业完成提交、排队/运行状态查看、日志、资源使用、取消、克隆、确定性诊断、项目评价和只读 AI 工作台；Windows 客户端也已经形成“登录 107 -> 部署远程服务 -> 建立隧道 -> 独立窗口打开 Dashboard”的完整实现路径。

但是，当前仓库还不能直接作为最终参赛提交物。主要原因不是核心代码缺失，而是最终提交的证据链和交付整理尚未闭合：

1. 演示视频和 PDF/Word 作品简介尚未放入仓库外层提交包；
2. 算力集群运行数据目前分散在项目文档中，尚未整理为一份评委可直接阅读的独立说明；
3. 最新 Windows 客户端的真实 107 交互验收仍需账号持有人完成；
4. 当前工作区存在未提交改动，本地试包来自脏工作区，不能作为最终可复现版本；
5. 学校真实 AI Provider 的地址、模型和凭证调用尚未形成可展示的真实验收证据。

因此，项目目前的判断是：**代码接近可演示，材料和最终发布门禁尚未完成；暂不直接上传最终比赛压缩包。**

## 三、评分维度审视

### 1. 创新性：中上，需强化真实场景叙事

目前最有说服力的创新组合不是单独的“Dashboard”或“接入 AI”，而是以下闭环：

- 以 Slurm、作业日志、usage 和 owner 元数据组成可信事实链；
- 先给出可追溯的确定性诊断，再让只读 AI 做解释和项目级评价；
- AI 不可用时，作业管理和确定性诊断仍可运行，核心流程不依赖模型；
- 通过 Windows 独立客户端、SSH 隧道和用户目录部署，降低本科生使用远程算力平台的门槛；
- 将作业提交、运行观察、日志排障、资源对比和多实验评价放进同一工作台。

方案独立性和技术思路已经具备，但“学科交叉创新”还没有充分落到一个具体参赛故事。演示和作品简介应选择一个真实、可复现的场景，例如 GPU 训练实验对比、CUDA OOM/超时诊断或本科生 GPU 实验教学，并用实际作业数据说明为什么传统命令行流程不够直观。

### 2. 实用性：中上，真实客户端验收是关键

核心用户问题明确：学生需要知道作业是否排队、为什么失败、资源是否够用以及如何复用或停止作业。作业列表、详情、日志、资源统计、诊断和项目评价已经形成连续流程，桌面客户端也有托盘、远程停止、更新和恢复入口。

当前的实用性风险集中在交付体验：

- Windows 端依赖 Microsoft Edge WebView2 Runtime，当前 EXE 没有把 Runtime 一并打包；
- 真实 107 的双因素认证、SFTP 二次认证、动态端口、WebView2 页面和托盘恢复仍需现场确认；
- 浏览器端真正的端到端自动化测试较少，录制视频前必须人工走完整流程；
- 登录窗口的系统明暗主题适配仍不是已验证完成的验收项。

### 3. 技术难度：较强

项目覆盖 React/Vite/TypeScript、FastAPI、SQLite、原生 Slurm、Python venv、SSH.NET、SFTP、SSH 隧道、tmux、WPF、WebView2、便携发布和版本化远程部署。架构上已经按 API、schema、service、repository、Slurm adapter 和前端功能边界拆分。

安全和可靠性边界也有明确证据：单 Unix 账号与有效 UID 校验、结构化 Slurm 参数、owner 范围、幂等记录、审计链、受控日志路径、SHA-256 服务包校验、版本目录、失败回滚、更新锁和本地启动缓存。它们应在作品简介中用一张架构图或一段简洁流程说明呈现，否则评委可能只看到一个常见的作业面板，而看不到工程难度。

### 4. 完成度：代码接近演示完成，提交闭环尚未完成

已有平台证据包括：

- Job `21482`：真实 GPU 作业资源和状态记录；
- Job `24011`：最小真实提交完成，退出码 `0:0`，并完成受控日志读取；
- Job `24063`、`24064`：真实取消验收；
- Job `24159`：真实完成作业，含日志和 usage；
- Job `24160`、`24161`：取消和克隆后的控制验收，且没有遗留活动验收作业。

已有测试/构建证据包括：Windows 客户端核心测试 9 项通过，相关发布脚本测试通过，客户端构建成功；用户提供的最新远程安装日志显示服务包检查通过并完成 `293 passed`。这些证据说明项目基础较扎实，但不能替代最终提交前的同一版本验收。

需要明确区分环境：在 Windows 开发机执行后端全量测试时，记录为 `282 passed, 13 failed, 1 skipped`；失败集中在 Windows 缺少 `os.geteuid()` 和创建符号链接权限，属于 Linux 专属测试在 Windows 上的环境限制，不能据此宣称“Windows 本地后端全量通过”，也不能据此推断 Linux 目标环境失败。最终应以 107/Linux 上同一干净版本的完整结果为准。

## 四、提交前必须闭合的门禁

### P0：补齐外层提交材料

建议最终压缩包内部结构如下：

```text
设计文档/
  项目设计与技术架构.md 或 PDF
作品简介.pdf 或 作品简介.docx
演示视频.mp4
算力集群运行数据说明.md 或 PDF
可部署程序/
  107Dashboard-Windows-x64.zip
  107Dashboard-Windows-x64.zip.sha256
  README.txt
源代码说明/
  Gitee 仓库地址.txt
  源码提交或标签.txt
校验和.txt
```

外层文件名应由队长按通知格式填写：

```text
队长学号+队长手机号+算力平台赛道+本科生队伍.zip
```

如果是研究生队伍，将最后一段替换为 `研究生队伍`。手机号和队伍类型属于提交信息，不能在仓库文档中写入真实值。

### P1：锁定最终代码版本

当前 `codex/windows-client` 包含 Windows 客户端、便携发布、远程部署缓存、前端构建和发布脚本等相对 `master` 的功能提交，但工作区仍有未提交修改和未跟踪源文件。当前 `data/releases/`、`data/windows-client-build/` 等是被忽略的本地构建产物，不能作为源码版本的替代品。

正式构建必须按以下顺序执行：

1. 先检查 `git status --short`，确认只有预期的源文件改动；
2. 将 Windows 客户端、发布脚本、前端构建脚本及对应测试作为一个可审阅的功能集合提交；
3. 在 Linux/107 上从该提交重新安装并跑完整后端测试；
4. 用 `--require-clean` 构建 Windows 客户端和服务包；
5. 记录 EXE、ZIP、服务包和校验文件的 SHA-256；
6. 用同一套产物完成最后一次真实 107 验收，然后再制作外层比赛压缩包。

如果构建脚本输出 `dirty working tree` 或 `local trial package`，就说明这不是最终可复现发行版，应先停止上传。

### P1：完成最新 Windows 客户端的真实 107 验收

账号持有人使用最新 EXE 至少走完以下链路：

1. 首次输入主机、账号、私钥并完成动态验证码认证；
2. 首次上传、SHA-256 校验、远程安装和服务启动；
3. 在独立 WebView2 窗口打开 Dashboard，确认页面和 API 都通过隧道；
4. 关闭并重新打开客户端，确认命中 `data/deployment-cache.json` 后只执行轻量服务探测；
5. 停止远程服务后重新连接，确认探测失败会清理缓存并自动走恢复流程；
6. 点击更新时确认仍会强制完整更新；
7. 验证最小化到托盘、恢复窗口、停止服务、断开连接和退出后的资源释放；
8. 记录异常时的脱敏日志，不要把验证码、私钥、口令或 Provider Key 放进提交材料。

### P1：形成独立算力运行数据说明

说明文件至少应包含以下列：

| 字段 | 内容 |
| --- | --- |
| Job ID / 作业名称 | 例如 `24159`、`24160`、`24161` |
| 分区 / QoS | 实际提交的 Slurm 分区和 QoS |
| 申请资源 | CPU、GPU、内存、时间上限 |
| 排队情况 | 提交时间、开始时间、排队等待时长；若平台没有精确值则说明计算口径 |
| 运行时长 | 实际开始到结束的时长 |
| 运行节点 | Slurm 分配的节点 |
| 终态 / 退出码 | `COMPLETED`、`CANCELLED`、`0:0` 等 |
| usage | 峰值内存、CPU 时间、GPU 或分配资源 |
| 日志摘要 | 只放脱敏后的几行结果，不放秘密和无关个人路径 |
| Dashboard 证据 | 页面截图或终端回执，能够对应 Job ID |
| 清理结果 | `squeue -u "$USER"` 无遗留测试作业 |

该文件的目标是让评委不需要阅读全部开发日志，也能确认作品确实在本科生算力平台的 Slurm 集群上运行过。

### P1：核实 AI 展示口径

作品简介和演示中必须写明模型名、OpenAI-compatible API 协议、Endpoint 类型以及 AI 的具体作用。当前仓库已经实现只读 AI 边界，但学校真实 Provider 地址和凭证仍待真实性验收，因此不能把模板地址或本地可用状态描述为学校平台已经正式接通。

推荐准备两个短场景：一个展示 AI 根据已选结构化证据解释诊断或比较结果，一个暂时关闭 Provider 展示“AI 不可用但作业管理和确定性诊断仍可用”。这样可以证明 AI 是增强能力，不是 Slurm 控制链的单点依赖。

## 五、分支、master 与正式发行版

当前仓库的默认分支名称是 `master`，不是 `main`。`codex/windows-client` 上的客户端和发布能力属于比赛交付链的一部分，最终应合并到 `master`，否则：

- 默认分支不能代表评委拿到的最终源码；
- 设计文档、构建脚本和可部署程序难以对应到同一版本；
- 后续从 Gitee 默认分支或标签复现发行版会产生歧义。

但**现在不建议直接合并整个工作区**。正确做法是先完成真实客户端验收，整理并提交这条功能线的源代码和测试，确认 Linux/107 验收结果，再通过普通合并或 Pull Request 合入 `master`。合并前必须保留其他未完成改动，不能用清理命令覆盖它们。

正式发布版需要合并的是：

- Windows 客户端源代码；
- 服务包和 Windows 发布脚本；
- 前端构建脚本、发布验证逻辑和对应测试；
- 用户可复核的 README/部署说明和本审查文档。

正式发布版不需要把以下内容提交到 Git：

- EXE、便携 ZIP、服务包和临时构建目录；
- 本机 `data/` 下的数据库、WebView2 数据、连接配置、缓存和日志；
- 任何私钥、验证码、口令、API Key 或真实运行时配置。

推荐的版本关系是：

```text
完成验收
  -> 提交功能线源代码
  -> 合并到 master
  -> 从合并后的干净提交打 tag
  -> 用 --require-clean 构建发行版
  -> 用同一发行版做最终 107 验收
  -> 把程序和材料放入比赛外层压缩包
```

也就是说，**发行版本身不必塞进 `master` 的源码历史，但发行版对应的源码和构建脚本必须进入 `master` 或一个明确的发布标签**。这比把一个未提交的本地 EXE 当作“正式版”更容易复核，也更适合后续更新。

## 六、收尾判断

当前可以给项目下的结论是：

> 107 Dashboard 的功能实现、技术栈、Native Slurm 安全边界和真实平台历史证据已经足以支撑比赛 MVP；项目在创新性和技术难度上有可讲清楚的亮点，实用性和完成度也具备基础。最终成绩的主要风险已经从“有没有核心功能”转为“能否用同一干净版本完成真实客户端验收，并按通知一次性提交完整材料”。

提交前只需要围绕本文件的 P0/P1 门禁收尾，不再继续扩展与比赛核心流程无关的生产化基础设施。登录页主题、移动端细节、浏览器自动化和代码签名属于体验或赛后增强项；除非真实验收暴露阻断问题，否则不应挤占最终视频、运行数据和清洁发布的时间。
